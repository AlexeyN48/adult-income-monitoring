# Мониторинг ML: Adult Income

Статус: идея и датасет согласованы пользователем. Реализация идёт последовательно по блокам; после каждого блока оркестратор проверяет результат и передаёт пользователю команды Git. Следующий блок начинается после обратной связи пользователя.

## Цель и требования

Обучить CatBoost на Adult Census Income и построить локальный воспроизводимый стенд мониторинга. На защите показать:

1. Обнаружение дрейфа признаков через Evidently.
2. Обнаружение изменения баланса целевых классов через Evidently.
3. Анализ fairness по `sex` через метрики и проверки в отчёте Evidently.
4. Графики F1 и результатов мониторинга в интерфейсе Prometheus.
5. Реальное срабатывание правила Prometheus, переход Pending → Firing и снятие алерта после восстановления.

Первое изображение пользователя — задание. Второе — вспомогательный материал. Airflow, MLflow и Grafana не входят в обязательный объём. Уведомления в сторонние сервисы и Alertmanager не требуются для демонстрации состояния Firing в Prometheus.

## Данные и модель

- Источник: UCI Adult, https://archive.ics.uci.edu/dataset/2/adult (CC BY 4.0; сохранить атрибуцию).
- Цель: `income > 50K`, положительный класс = 1.
- Модель: CatBoostClassifier с фиксированным seed и сохранёнными параметрами.
- Нормализовать пробелы, завершающую точку меток в adult.test и обозначения пропусков.
- Сохранить раздельные train, validation, reference и current. Не допускать пересечения исходных записей между этими частями. Варианты current могут использовать одни исходные записи для парного сравнения; это явно документируется.
- Train используется для обучения, validation — выбора порогов; reference и current — только для мониторинга. Если используется официальный test, не смешивать его с train при подготовке.
- `sex` сохраняется для аудита, исключается из входов модели. Это само по себе не гарантирует fairness: другие признаки могут служить прокси.
- Reference фиксирован; current подаётся последовательными учебными пакетами. Это симуляция потока, а не реальные временные наблюдения.
- В учебных пакетах настоящая целевая метка доступна сразу. В реальном сервисе F1 и TPR могут стать доступны только после получения разметки.

## Сценарии и корректность демонстрации

- `baseline`: неизменённый current с исходными метками и предсказаниями модели.
- `feature_drift`: возраст +5 лет по заданию; интенсивность настраивается. Если такой сдвиг не пересекает порог, показать фактический результат и отдельно усиленный сценарий. Не подменять статистический вывод.
- `target_drift`: изменить долю классов выборкой по настоящим меткам, не переписывая метки. Обеспечить достаточный объём каждой группы и класса; повторы внутри искусственного сценария, если нужны, раскрыть в отчёте.
- `fairness_shift`: контролируемое смещение состава одной группы. Сначала измерить его влияние на реальные предсказания. Если нужен гарантированный показ нарушения, отдельным явно обозначенным сценарием ввести синтетический дефект принятия решения для одной группы; сохранить исходные предсказания и параметры дефекта. Не выдавать такую демонстрацию за естественное поведение CatBoost.
- `recovery`: вернуть baseline и дождаться снятия соответствующих алертов. Если baseline уже нарушает пороги fairness, зафиксировать это и отделить постоянное нарушение от дополнительного ухудшения; не обещать снятие такого алерта без устранения причины.

Сдвиг баланса классов не равнозначен дискриминации. Fairness-метрики — индикаторы различий между группами, а не доказательство причинной или юридической дискриминации.

## Метрики и правила

- F1 для положительного класса, дополнительно macro-F1 и размеры пакетов.
- Evidently: дрейф отдельных признаков, доля дрейфующих признаков; отдельная проверка дрейфа target (не смешивать target с входами модели).
- Fairness: доля положительных предсказаний в каждой группе, demographic parity difference, disparate impact ratio и TPR gap. Зафиксировать формулы, порядок групп, обработку нулевого знаменателя и минимальный размер группы/число положительных меток.
- Пользовательские fairness-метрики и пороги должны исполняться в системе метрик/проверок Evidently и присутствовать в отчёте. Недостаточно отдельно вычислить число и только отправить его в Prometheus.
- Не интерпретировать неопределённую метрику как нулевой риск. Публиковать пригодность пакета для оценки и давность последнего успешного расчёта.
- Порог F1 выбрать по validation до финальной демонстрации, документировать. Пороги статистических тестов и fairness — учебные настройки с объяснением. Числа не подгонять молча под выбранный current.
- Предусмотреть алерты на дрейф, низкий F1, нарушение fairness и недоступность/устаревание мониторинга. Минимальный обязательный показ — реальный Firing, вызванный рассчитанными метриками.
- Метрики извлекать из завершённого расчёта, обновлять согласованным снимком. Исключить высокую кардинальность labels и подстановку констант вместо результатов.
